# 文案生成器质量护栏

## 何时用
- 用户说"文案垃圾 / 一股伪人味 / 达不到要求 / 字数太少 / 全是套话"
- 用户说"不是说了不要重复吗"——重复检测漏报或误报
- 要给生成器加"≥N 种风格供用户挑"、"写完自己打分"
- 生成器有"离线兜底"分支，且离线产物质量明显差于在线
- 出现"AI 生成失败"但页面只显示一句无信息量的报错

## 核心心法
1. **离线兜底也是交付物**：没配 Key 时用户看到的就是它。它必须有风格、有结构、无病句。
2. **宁可少给，不给碎片**：数据不足以支撑 N 段时，主动少给段数并**在 note 里说明原因**，而不是硬切成 20 字的半句话。
3. **不许自我安慰式打分**：如果评分给"豆瓣简介＋风格外壳"打 99 分，这个分对用户毫无用处，还会掩盖问题。
4. **标尺先量用户的稿**：任何"达标线"（字数/段数/评分维度）都要先拿**用户的参考稿回测**一遍。
   如果用户自己的稿子都不达标，那是标尺错了，不是稿子错了。
5. **失败必须可归因**：任何降级都要把原因带到 UI 上（`note`/`warning` 字段），否则用户只会说"又失败了"。

## 七类真实缺陷与修法（都踩过）

| 缺陷 | 反例 | 修法 |
|---|---|---|
| 裸连词造病句 | 「**而1994年，香港回归前夕**」 | 承接词只用**带逗号的状语式**：`随后，/与此同时，/在这条线索上，/紧接着，/最终，`；数字、`《`、emoji 开头及「标签：」式清单句**不补**承接词 |
| 重复标点 | 「解散**。。**」「冲！**🔥。**」 | `_sent()` 补句号前先判尾字符：已是 `。！？…!?；;：`、右括号、引号、emoji（`0x1F000-0x1FAFF`/`0x2600-0x27BF`/`0xFE0F`）则不加；再统一 `_tidy()` 收 `。。`/`，。` |
| 合并粘连 | 「2026年上映**1.** 阵容靠谱」 | 拼段走 `_join2(a,b)`：a 以句末标点结尾直接拼，emoji 结尾补空格，否则补 `。` |
| 双书名号 | 「**《《**寒战1994**》》**」 | 风格模板里已含 `《%s》` 时，传参只给裸片名；统一 `mm = '《%s》' % name.strip().strip('《》')` |
| 尾部合并毁结构 | 想要「开场+事实 / 看点+收尾」，结果被 normalize 从**尾部**合并成「开场 / 事实+收尾」 | 段数 ≤2 时在组装阶段就合成 `[head+mid, tail]`，不要指望 `normalize` 猜 |
| 硬编号错乱 | 理由列表 `1./2./3.` 被并成一段后编号断裂 | 改 `；` 连接；且文案里的「给你 N 个理由」的 **N 要与实际条数动态对齐** |
| 硬切碎片 | 原文 80 字却要 3 段 → 20 字半句成段 | `eff_n = max(1, min(n, total // 46))`，46 字≈一段能读的最低字数；返回段数 < 请求段数时在 note 说明 |

## 诚实自评分口径（`score_copy`）
- 长度 25：以字数基线为满分线**线性**计分，短文案就该拿低分。**但基线必须先量用户的参考稿**——
  踩过的坑：按"用户说要 150 字/段"把基线定为 150，而用户自己的模板实测只有 **106~121 字/段**，
  结果把**用户的稿子也判成"偏短"**。标尺错的时候，扣分理由是在冤枉好稿。
  「提示词目标」和「打分基线」**不必是同一个数**：提示词可以往高了要，打分必须如实。
- 真实信息 35：用**正则精确匹配**（`豆瓣\s*[\d.]+\s*分`、`执导`、`主演`、`剧集`…），不要用 `'分' in text` 这种会被"十分/部分"命中的粗糙判断
- 具体细节 20 + 段落连贯 20：连贯判定要**接纳事实句/清单句开头**，否则风格化的开场永远被误判为"缺过渡"
- 扣分：套话黑名单 −40、**碎片（每段 <45 字）−10/段**、未提片名 −8
- 用法：`score < 60` → 把扣分原因拼成批评意见回喂模型重写（最多 2 轮）；重写后**只取更高分的那版**

## 「伪人味」：用户一眼就能看出来的四类病

用户说"文案一股伪人味"时，指的通常不是错别字，而是这几种**结构性**毛病：

| 病征 | 反例 | 修法 |
|---|---|---|
| 标签排比 | 「阵容与制作都在线：表演稳、节奏紧，完成度相当高」 | 删掉标签前缀，把信息写成话；同一句里别出现「XX：YY」并列 |
| 报数字＋贴万能好话 | 「豆瓣 8.0 分。这是一部不容错过的佳作。」 | 数字与结论之间必须有逻辑：**先事实、后判断** |
| 两段复述同一批数据 | 第 1 段写评分/导演，第 2 段又把评分/导演写一遍 | 两段**严格互补**：`_score_para`（评分/人数/导演）／`_crew_para`（主演/类型/片长/年份） |
| 给评价段硬补承接词 | 「随后，题材是剧情、喜剧、动画…」 | 承接词是**叙事**的需要；评价是"事实 + 观点"，补了就不像人话 |
| 跨风格措辞撞车 | 剧情说"最狠的一手藏在后面"，评价又说"看点简介里没写" | 剧情/评价的开场收尾**刻意换一批措辞**；风格差异要落在**事实切入顺序**上，而不是同一段话换个开场白 |

**正解：把数字翻译成判断（分档函数）**——这是离线唯一能立得住的"观点"，且完全基于真实数据、不编造：

```python
_rating_tier('8.0')   # → 「放在同档期里，属于口碑靠前的一档」
_rating_tier('6.9')   # → 「分数在及格线往上，属于有争议、但底子看得见的那类」
_count_tier(130000)   # → 「十万人级别的样本」
_runtime_tier('102分钟')  # → 「标准的院线体量，不拖，也不算赶」
```

组装出来的段落长这样，数字与判断之间有逻辑，才不像机器写的：

> 豆瓣 6.9 分，15万人打出。十万人级别的样本，分数在及格线往上，属于有争议、但底子看得见的那类。

**顺序不能反**：不要写「平心而论，它的底子是看得见的。豆瓣 8.0 分、13 万人打出。」——
先下结论再贴数据，读起来就是伪人味。

**两条路径必须同一水准**：抓取路径（用户没点 AI 按钮）与离线风格库要**复用同两个组装函数**，
否则会出现"不点 AI 就给另一种水平的稿子"。

## 重复检测（`find_repeated_phrases` / `collect_repeat_warnings`）的三个坑
- **字段要查全**：只查标题/标语/邀请语会漏掉最常出问题的地方——`highlight`（标题亮点）和**正文各段**。
- **别用"含片名就整条放过"**：`玩具总动员5·本周必看` 这类（片名 + 后缀）就是这么被放过的。
  正确做法是**摘掉片名后看剩余部分还够不够长**，够长才算真重复。
- **小心反向误报**：标题常由亮点拼成，拿「标题 ↔ 标题亮点」互比会**条条命中**。
  用 `skip_pairs` 显式排除这对；阈值也要分层：短字段 `min_len=3`、正文段落 `min_len=6`
  （否则人名/片名之间互相误报）。

## 多风格候选接口（"≥5 种风格供用户挑"）
- 风格库放后端：`{key: {name, desc, prompt}}`；`prompt` 既进 AI 的 system 提示，也驱动**离线**产出不同结构
- 保留 `_STYLE_ALIAS` 兼容旧风格名，老配置不失效
- 一个接口一次返回全部风格：`{options: [{key,name,desc,paragraphs,is_ai,note,quality,cost_cny}]}`，**按自检分降序**，第一名标「推荐」
- 前端渲染成可挑卡片（段数/字数/AI或离线/扣分点/「✔ 采用这一版」），点击回填到编辑区
- 配置接口顺带下发风格列表，前端动态渲染下拉，避免前后端两份风格名漂移

## LLM"生成失败"的排查顺序
1. **Key 到底有没有**：没配 Key 时系统常常**静默走离线兜底**——用户看到"生成出来了但味道不对"其实等于没接 AI。要在 UI 明确区分 `is_ai`。
2. **保存设置会不会把 Key 冲掉**：如果前端每次都提交 `api_key: input.value`，而 Key 输入框不回显（永远空），那**改任何其它设置都会静默清空 Key**。约定：`''` = 不改动，`null` = 显式清空。
3. **配一个「测试连接」接口**：`explain_net_error(e)` 读 `HTTPError.read()` 的 body，翻译成 401 Key 无效 / 404 地址或模型名错 / 429 限流 / 402 余额不足 / 超时 / 网络不可达 + **怎么修**。
4. 调用失败不白屏：自动降级离线风格库，并把原因写进 `note` 显示出来。

## 外部数据源兜底（抓取"失败"时）
- **四级兜底**：主接口指数退避重试 → 备用入口/搜索页 → HTML 兜底 → 才报错
- **失败不入缓存**：把"限流导致没找到"写进缓存会让同一关键词**永久**失败，必须重启进程（很隐蔽）
- **抓不全 ≠ 失败**：只要拿到部分真实数据就返回 success，用 `warning` 说明缺了什么
- **复用已有 skill**：`data-source-staleness-guard`（时效/停更护栏）、`offline-realdata-cache`（离线真实数据）

## 交付前自检清单
- [ ] **标尺回测**：把用户的参考稿喂进 `score_copy`，它必须拿高分；拿不到高分就是标尺错了
- [ ] 离线产物逐风格跑一遍，肉眼读，找病句/碎片/粘连/重复标点/伪人味
- [ ] 评价段逐条查伪人味：标签排比 / 报数字贴套话 / 两段复述同一批数据 / 硬补承接词
- [ ] **重复检测双向验证**：拿用户报过的实际重复串做 case 确认能命中；再拿一版正常文案确认**不误报**
- [ ] 短数据源 + 长数据源各跑一遍，段数与 note 符合预期
- [ ] 故障注入：主接口挂 / 备用也挂 / 只返回部分字段，三种情况都不崩且原因可读
- [ ] 有没有"同一份文案换风格名"的假多样性（断言至少 3 种产出不同文本）
- [ ] 「不点 AI」的抓取路径与离线风格库**同一水准**（复用同一批组装函数）
- [ ] 端到端：真实 HTTP 走一遍 抓取→生成→导出→**回读 docx 校验段落与图片落位**
- [ ] **把这次的缺陷写成回归测试**：用户点名的每个病征一条断言（如"套话黑名单零命中""无 <45 字碎片段"），
      否则下次重构会悄悄退回去
