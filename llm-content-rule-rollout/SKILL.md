# 多路径 LLM 文案生成：内容规则落地 SOP

## 何时用
用户要求改生成规则（如「评价不要写评分」「不要复述剧情」「聚焦情感与特点」），
而该文案由**多个路径**共同产生——只改一处，规则必然半生效。

## 第 1 步：先枚举全部生成路径（漏一处 = 规则半生效）
用 Grep 搜出所有产出该字段的位置，典型 6+ 处：
1. AI 单字段提示：`build_prompt`
2. AI 整块/多段提示：`build_block_prompt` + 段落结构表（如 `_BLOCK_STRUCT`）
3. 离线单字段兜底：`_fallback_ai`
4. 离线风格库正文：`_style_*_body`
5. 数据驱动的自动成稿：`_compose_*`
6. 质量自检评分：`score_copy`（匹配模式与阈值也要跟着改，否则自检与新规则自相矛盾）
7. 数据来源的 warning 文案 + 前端 hint + 文档
8. 测试：编码「旧行为」的断言必须一起改（如旧的「评价必须含评分」）

## 第 2 步：注入规则时，一并切断「诱导源」
- **不要把规则禁止的素材喂进提示**。反例：规则「评价不写剧情」，却仍把 `summary`
  当 fact 传给评价 prompt → 必然诱导模型复述。用 `kind != 'review'` 之类条件把它过滤掉。
- 检查结构表里的措辞：`"补一个具体细节（一场戏/一句台词）"` 会诱导模型讲情节，
  改成 `"谈怎么拍的（表演/镜头/声音/美术处理）"`。
- 模型有先验知识时会「凭记忆」违反规则（例：讲《霸王别姬》全剧情）。把禁止项写得
  **具体到「情节/人物命运/结局」**，并明确「谈怎么拍而非讲了什么」。
- 离线路径不知道剧情，天然守规；**出问题的一定是 AI 路径**——重点对抗测试它。

## 第 3 步：规则改了内容长度/构成 → 重校质量基线
自检里的「篇幅基线」（如 120 字/段）若是按**旧内容**定的，去掉一部分内容后必然扣分，
造成自检分虚低、测试变红。按新常态重校（例：评价本就更短，基线从 120 降到 80 字/段）。
顺带确认「碎片阈值」（<45 字）对这些风格是否合理——短平快风格的开场行要靠补真实信息撑够长度。

## 第 4 步：字数限定（当规则是「内容要多少字」时，四条硬经验）

「做字数限定」听起来像调个参数，实际最容易反复不合格。四条都是踩出来的：

1. **字数要求的位置比措辞更重要：必须放在 user 提示的最末尾。**
   同一句话放在提示中段（结构说明里）时模型只写到 6 成（目标 240 → 实际 160）；
   挪到末尾后立刻进区间。对照实验里三种不同措辞只要都放末尾就全部达标。
   → 做法：末尾追加一段「字数硬性要求（最后强调，直接决定合格与否）」。
2. **上下限必须对称给，并给「每段字带」。**
   只说「少于 180 字视为不合格」→ 模型会冲到 305 字（超上限 300）。
   正确做法：`每段 ceil(min/n)–ceil(max/n) 字`，n 段 × 字带恰好等于整篇区间，天然自洽
   （例：180–300 / 3 段 → 每段 60–100 字）。
3. **风格提示里的「句子要短」会被误读成「篇幅要短」**——这是模型写短的真正根因。
   必须显式澄清：`"句子要短"只指单个句子简短利落，不是让整段缩水`。
4. **重写循环别做成「重新掷骰子」，要做「定向修订」。**
   两个常见错：① 只把 critique 追加到原 user 后，模型看不到自己上一版 → 长度又是一次随机结果；
   ② 取舍口径只比质量分，而篇幅在自检里只占一小部分权重 → 「补足字数」的重写反被判定
   「提升有限」丢弃。修法三件套：
   - 长度独立成闸门（`_len_report()` 返回 `是否在区间 / 实际字数 / 区间`），不靠评分间接体现；
   - 取舍排序改为 `(是否达标, -离区间差多少字, 质量分)`，先达标、再逼近、最后比质量；
   - 重写提示里**把上一版原稿原样贴回去**，并二选一给明确动作：
     「保持内容与段落顺序不变、每段扩写到 X–Y 字（现在分别是 …）／保留全部真实信息、压缩到 X–Y 字」，
     并明令「不许新增段落／不许删掉真实信息」。
   实测命中率 0/2 → 12/12，且多数情况连重写都不需要。

配置语义要分清并在 UI 说清：**可配的那个数是「目标值」（瞄准点），
`_WORD_RANGES` 是「硬性合格区间」（真卡线）**。否则用户设了 400 却拿到 240 会以为坏了。

## 第 5 步：结构上杜绝回灌
删掉只服务旧规则的函数（如纯评分的 `_score_para`/`_count_tier`/`_rating_tier`），
别留成"死代码"——否则以后容易被人再次调用，规则悄悄失效。

## 第 6 步：验证 = 检测器 + 多路径 + 对抗样本
写小脚本跑：
1. 命中规则关键词即判失败；**注意误命中**：`\d+\s*分` 会命中「171**分钟**」，要排除。
2. 同时覆盖 AI 路径（`/api/...` 实测）与离线路径（直接 import 调函数）。
3. 拿「会违反规则的样本」（长简介 + 评分）做对抗测试，而非只跑正常输入。
4. **字数类规则要多轮取样**：温度 0.8 下单次结果不能代表命中率，
   每种「类别 × 段数」至少跑 3 轮，报「n/N 命中」而不是「跑通了」。
   顺手把「字带 × 段数 == 整篇区间」写成断言（纯算术，零成本，永远能跑）。

## 常见同源问题：配对字段「各生成各的」→ 必然雷同 / 不成对
当两个字段是**视觉/语义配对**（如 slogan1/slogan2、主标题/副标题、两段评价），
若各自独立点生成按钮（两次调用、互不知对方内容），结果极易撞车、近义，或凑不成一对。
- **解法：同一次调用产出两句**（给模型"只输出两行：第一行＝上句、第二行＝下句"），
  模型看得见两边，才可能真给出成对的两句。
- **明确"搭配关系"**：不只是"角度不同"，而要"成一对"——对仗／递进／呼应，主题一致、语气一致、用词不重复。
  典型分工：上句抛主题/情绪/悬念，下句承接/呼应/升华。
- 解析后**校验**：若两句重复或只给一句 → 用备用/离线句补齐，绝不让两句一样或不成对。
- 离线兜底也要是"一对"（如「暗场之后，另一个世界开始」/「散场之后，有些话还没有说完」）。
- 把真实资料（类型/导演/主演/年份/梗概）注入提示 → 贴合对象特色，而非通用套话。
- 改完把 UI 上两个按钮都指向"成对生成"入口，label 标清「上句/下句」，并说明点任一个都会同时重拟两句。

> 相关：当「配对字段」不止两个，而是要把风格/版本扩到几十种并支持多选批量生成时，
> 见 skill `multi-style-generation`（成本闸门 / 离线塌缩 / 并行加速三件事）。

## 硬经验：测试绝不能改写真实密钥
跑 `pytest` 时，若测试调 `/api/ai_config {api_key:None}` 之类会**落盘到线上 `config.json`、
清掉真实 Key**（本类项目踩过一次，Key 被清空）。
- 修法：让配置路径可被环境变量覆盖
  （`CONFIG_PATH = os.environ.get('XXX_CONFIG_PATH') or 默认`），
  测试在 `import app` **之前**把环境变量指向临时文件。
- 跑测试前**先备份 config.json**，跑完校验 sha256 前后一致。
- **备份必须在第一次跑测试之前做**——跑过一次就已经被清空了。
- 临时配置加入 `.gitignore`。

## 交付口径
按「路径 | 是否已改 | 证据」列表汇报，跑通测试后给出 通过数 + config sha256 一致性，
不要只说「改好了」。
