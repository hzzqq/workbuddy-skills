# 长任务后台运行与判活

## 目的

长任务（模型训练、回测扫描、批量构建）有两个高频误判，都会浪费大量时间：

1. **静默真死**：进程已死但没写任何错误，日志停在半路 —— 被误认为"任务太慢，再等等"。
2. **静默假死**：进程好好的、正在全速算，只是**日志按 epoch/阶段打印**，中间几分钟无输出 —— 被误认为"挂了，重启"。

两者的外部表征几乎一样（日志不动），**判活方法错了就必然误判其中之一**。

## 一、启动：让进程活过工具调用

**核心规则：后台长任务必须用运行环境的托管式后台机制，不要用 shell 的 `&`。**

| 做法 | 结果 |
|---|---|
| `nohup python x.py > log 2>&1 &` | ❌ **子进程随工具调用返回被清理**，表现为日志停在半路、进程消失、无报错 |
| `setsid python x.py &` | ❌ 多数精简 Git-Bash / 容器环境**没有 setsid**（command not found） |
| `cmd /c start ...` / 写 `.bat` 双击 | ⚠️ 可行但绕远，且 Windows 下非 ASCII 路径有编码坑 |
| **工具的 `run_in_background: true`** | ✅ **首选**。由环境托管，跨工具调用存活 |
| 前台跑（等它结束） | ✅ 若任务时长可接受，最省心 |

补充要点：
- 务必加 **`-u`**（或 `PYTHONUNBUFFERED=1`）。不加则 stdout 块缓冲，日志会滞后几 KB 才落盘，判活更难。
- 用 `2>&1 | tee <logfile>` 同时保留实时输出与落盘副本，便于后续引用。

## 二、判活：只看 CPU 时间增量

**唯一可靠判据是「进程的 CPU 时间是否在增长」。**

不要用：
- ❌ **日志文件时间戳** —— 阶段式打印下，几分钟不动完全正常。
- ❌ **内存占用** —— 已完成数据加载、正算小批量时内存可能反而下降。
- ❌ **`tasklist` 里进程存在** —— 只说明没退出，不代表在算（可能卡在锁/IO 等待）。
- ❌ **`wmic process`** —— 常被程序黑名单禁用。

直接运行本 skill 自带的采样脚本：

```bash
python scripts/check_alive.py                 # 自动挑内存最大的 python 进程
python scripts/check_alive.py --pid 12345     # 指定 PID
python scripts/check_alive.py --name python.exe --sample 20
python scripts/check_alive.py --pid 12345 --json   # 机器可读
```

### 结果判读

| 采样窗口内 CPU 增量 | 含义 |
|---|---|
| ≈ 线程数 × 窗口秒数（如 8 线程 / 12s 约 +96s） | ✅ 满载训练，一切正常 |
| 明显小于线程数（如 +1s） | ⚠️ 卡在 IO / 锁 / 网络等待，或已实质停滞 |
| ≈ 0 | ❌ 进程空转或已僵死，需排查 |

> 退出码：`0` = 在跑；`1` = 空闲/停滞；`2` = 找不到进程。可直接用于脚本判断。

## 三、区分「脚本有问题」与「只是启动方式有问题」

若判活显示进程已死，**先用前台重跑一次**再改代码：

```bash
python -u script.py --smoke      # 前台 + 无缓冲，真实报错会立刻打印
```

- 前台能正常推进 → **代码没问题**，是启动方式（`&` 被清理）的问题。
- 前台也报错 → 才是代码问题。

这一步能把排查范围砍一半，避免去改根本没坏的代码。

## 四、脚本侧设计：让长任务可恢复

若长任务是自己写的脚本，优先做到：

1. **分阶段落盘**：训练完立刻保存模型/中间结果，再做回测/评估。
   这样后段被杀也不丢前段产物。
2. **提供恢复入口**：单独的 report 脚本可从已落盘产物重建最终报告。
3. **阶段级日志**：每个 epoch / chunk 打印一行（含耗时），便于粗判进度；但记住它**不能替代** CPU 判活。
4. **异常兜底**：顶层 `try/except` + `logger.exception`，把栈写进日志。
   注意：进程被外部**强杀**时这层兜不住，所以判活仍要靠 CPU 采样。

## 五、判定流程速查

```
启动长任务
  └─ 用托管式后台（run_in_background）或前台，加 -u
       └─ 日志不动？
            ├─ 正常（阶段式打印）→ 采样 CPU 增量确认在跑 → 继续等
            └─ 采样 CPU 增量为 0
                 └─ 前台重跑 --smoke
                      ├─ 正常推进 → 启动方式问题，换托管式后台重跑
                      └─ 报错 → 代码问题，读栈修复
```

## 六、平台差异备注

本 skill 的采样脚本面向 **Windows**（`tasklist` + `GetProcessTimes`）。
在 Linux / macOS 上改用等价命令即可，判活逻辑不变：

```bash
# Linux / macOS：比对两次采样
cat /proc/<pid>/stat | awk '{print $14+$15}'   # utime + stime（jiffies）
ps -o pid,time,etime,%cpu -p <pid>             # 或看 TIME 列是否增长
```
